# Studio

The Studio (studio.md § The Studio home, § The package workspace), only at central. It starts from what is designed (#855); the package workspace (#492) is its Packages section, at `/studio/packages`. An edge or a desktop shows that the Studio is not there (`capabilities.studio`), and neither serves `/api/studio`.

- **`StudioHome`** (`/studio`, #855): one card per kind of design (Forms, Workflows, Concepts & value sets, Decision tables, Programs, Age band sets), each with its description, how many there are (`GET /api/studio/designs`, `designs.ts`), *Open* and *New*; Indicators, Reports and Dashboards marked *Coming soon*; and Packages.
- **`DesignSection`** (`/studio/forms`, `/studio/workflows`, `/studio/concepts`, `/studio/decision-tables`, `/studio/programs`, `/studio/age-bands`; `?new=true` opens *New*): every design of the section's kinds across packages, each in the version it opens in (its package's open draft, else its latest published version), with title, package, status (published, in your draft, in someone else's draft, submitted) and last change, a search, a package filter and a status filter. A row opens its editor (a decision table opens the Workflow Studio at `?table=`). *New* (`create.ts`) asks for the package (a draft the person holds, a published package whose next version it starts, or a new package) and a title (and, for a decision table, its workflow), saves the new design with `If-Match` and opens it.
- **`EditorBar`**, above every editor (its route renders it, and remounts the editor per package version): the package, version and stage, a link to the draft page, and, read only, *Edit*, which reopens the person's draft or starts the next version of the published package (`POST /drafts` with `copyOf`) and reopens the editor there; or who holds the draft, or that it is submitted.
- **`PackagesPage`** (`/studio/packages`): a DataTable with one row per package, its newest version not withdrawn: title, name and kind; version and semver bump; status; its Draft Holder; **your next step**, or "Nothing for you"; and the scopes it is active in. A click on a row, or Enter, opens the package.
- **`PackagePage`** (`/studio/$id`, `id` is `name@version`; its back link goes to the packages), read from top to bottom:
  1. **What changed:** each added, changed or removed artefact against the latest published version before this one; under a changed one, each element path that changed with the server's one-line summary and the bump it needs (#495). The Draft Holder's one change note for the whole draft sits above them, edited in place with `If-Match` (`PUT …/note`) while the draft is editable.
  2. **Is it safe?** The stored validation and simulation results, the heading counting the failing ones, each marked when the draft changed since it ran.
  3. **Who must act:** the reviewer, the approvals given and needed, then every action. One the person may not take stays on the page, disabled, with the server's reason, e.g. "You wrote this draft, so you cannot review or approve it". *Request changes* asks why and *Activate* asks for a scope.
  4. **Discussion:** the draft's one thread (#496): the history the lifecycle writes, with the comments among it, oldest first. A comment may name one of the draft's artefacts, which links to its editor (form designer, terminology browser, Workflow Studio or file editor). Below it, a box for a new comment and the artefact it is about (`POST …/comments`); the server writes the entry. Closed, with the reason, once the draft is published or withdrawn.

  Under the title it names the **Draft Holder** (#493), and a handover waiting to be accepted. Only the holder edits, checks, submits, hands over or withdraws the draft. *Hand over* asks for a username, and the draft stays with its holder until that person presses *Accept the handover* (their next step); either of them may *Call off the handover*. *Reassign*, with `metadata.manage`, gives the draft to a username at once and asks why. *Withdraw* ends the draft: the page moves to the id it is kept under, read only, and its version can be drafted again. Everyone who has held the draft is an author, so none of them may review or approve it.

  It also lists the package's **files**, each opening in the file editor. In a draft the person may add a file and change the version; a published version offers *Start the next version*, a copy at the next minor `-draft` version. *Check now* is one of the actions: it stores validation and simulation results and leaves the draft a draft.
- **`FileEditor`** (`/studio/$id/files/$`, the splat is the file's path): one file as JSON text. *Save* sends that one file with the revision it was read at as `If-Match`; if someone saved the draft since, the server answers 412, nothing is kept, and the person reloads. A path the draft does not hold opens empty and is added on its first save. Read-only when the server says the person may not edit (`editable`, `editRefusal`).
- **`forms/FormDesigner`** (`/studio/$id/forms/$`, #497 part 1; studio.md § The form designer): a Questionnaire of the package, opened from its line in *What changed* or in the files.
  - **Left:** the questions grouped by Form Layout section, those in no section last (they show at the end of the form), with up and down, *Add question* (into the selected question's section) and the sections themselves (add, retitle, reorder, remove).
  - **Middle:** the selected question in three groups. *Question* (clinical, approved with the package's kind): text; id, fixed once the previous published version has it (renaming a new one carries its conditions and layout entries along); answer type; required; more than one answer and options for a choice, or a bound ValueSet (`forms/ValueSetPicker.tsx`, part 3: the picker searches the ValueSets this package version may bind, published or drafts of the same package, previews the codes, suggests a widget and records `url|version`, replacing the question's own options); shown only when a yes/no question is Yes. *Layout*: section, widget (those that fit the type), hint. *Becomes a record* (`forms/record.ts`, part 2): the records the answer becomes under the package's Extraction Mapping (the top-level Library whose `extraction-target-questionnaire` is the form), each a contained template whose `templateExtractContext` ends on the question's linkId, with its resource type and code; the code is edited, a managed Observation whose value is the answer is added (the mapping file, `Library-<name>-mapping.json`, on first use), and a record is removed. Whatever else a template says is kept.
  - **Right:** the live preview in the real `QuestionnaireRenderer`, remounted on every change, given the codes of each bound ValueSet as the terminology service expands them.
  - **Above:** the problems found while editing (`forms/model.ts`'s `problems`): duplicate or empty ids, a question with no text, a choice with no options, a condition on a question that is not yes/no, a widget that does not fit, a question in no section, a published question removed, a section with no title, a record with no code or of a question no longer in the form. *Check now* remains the authority.
  - **Import FHIR JSON** (`forms/importing.ts`, part 2) replaces the form with a pasted Questionnaire, read by central as R5 or as R4 converted to R5 by `health-fhir-mapping` (`importQuestionnaire`, #853; no R4 code lives in the client). The server's conversion report lists what was converted, and anything unconverted (an unknown element or type, contained resources, a modifier extension) blocks the import. The draft keeps its id, url, version and status, the source canonical goes to `derivedFrom`, and the layout drops questions the new form lacks.
  - **Saving** goes through the file editor's path: the Questionnaire, then its Form Layout (the `configuration/` file naming its `url`, or `configuration/FormLayout-<name>.json` once a section, widget or hint is chosen), then its Extraction Mapping, each with `If-Match`; a 412 keeps nothing and asks to reload. What the designer does not edit (extensions, expressions, other conditions, nested groups' settings) is kept as read.
- **`terminology/TerminologyBrowser`** (`/studio/$id/terminology/$`, #523; studio.md § Terminology): a CodeSystem or ValueSet of the package, opened from its line in *What changed* or in the files.
  - **Left:** the code systems the package is authored against (`GET …/terminology/code-systems`): its own and those of the latest published version of every other package, each local or external (from a terminology package, read only), with its version and concept count.
  - **Middle:** the selected code system's hierarchy, one level at a time, and search by code or words. Both run on the server a page at a time (`GET …/terminology/concepts`), so ICD-11 never loads in the browser. The selected concept shows its display, definition, parents and the ValueSets that contain it (`GET …/terminology/concept`). With a draft ValueSet open it is added alone, added with everything under it (an `is-a` filter, so later child codes follow), or excluded; concepts already in the ValueSet are ticked.
  - **Right:** the open ValueSet (or, from a CodeSystem, the package's ValueSets and a new one): its rules, each removable; its expansion; the change against its expansion in the package's previous published version, removed codes flagged; and the form questions that bind it (`POST …/terminology/expand`, which expands the unsaved ValueSet). *Save* goes through the file editor's `If-Match` path.
  - **A local CodeSystem of the draft** (`terminology/CodeSystemEditor`, #524): the tree gains *Add a code* and *+ under*, and the concept panel becomes a form (code, display, definition, parent, and a note for reviewers that goes to the discussion). Each edit is saved on its own (`POST …/terminology/edit`, `If-Match`); the server refuses a published code (`fixed`) deleted, renamed or moved, so the form offers it only *Retire*. Beside the tree, *Version* gives the next version and why, and *What it reaches* each ValueSet drawing on the code system with the codes it gains or loses and the forms that bind it (`GET …/terminology/code-system-change`). External code systems stay read only.
  - `terminology/model.ts` edits the compose and keeps what it does not edit. `terminology/api.ts`'s `valueSetsQuery` and `expandValueSet`, with `suggestWidget` (radio up to 7, drop-down up to 30, search beyond) and `bindingOf` (`url|version`), are what the form designer's ValueSet picker (#497 part 3) uses.
- **`workflows/WorkflowStudio`** (`/studio/$id/workflows/$`, #498 parts 1 and 2; studio.md § The Workflow Studio): a top-level Library of type `workflow-definition`, opened from its line in *What changed* or in the files (the draft page reads the package's Libraries to find them). The route is its own chunk, so `@xyflow/react` and dagre load only there.
  - **Left:** the states as a tree, each with its exits (target, event or timer, guard); *Add a state*, and *Add a state inside* a compound or parallel state.
  - **Middle:** the canvas (`workflows/WorkflowCanvas.tsx`): `@xyflow/react`, laid out left to right by `workflows/layout.ts` with dagre, compound and parallel states as groups holding their children. Dragging from a state's right edge to another adds a transition. Problems are outlined in red. React Flow's attribution link stays; zooming on scroll is off.
  - **Right:** *Inspect*: a state's id (fixed once the previous published version has it; renamed when the field is left, its references following), kind, parent, initial child, what happens there (wait, human task, payment gate, sub-workflow), entry actions and its exits with *Add a transition*; or a transition's source, target, trigger (event, timer of its source state, eventless), FHIRPath guard with the declared data it may read, the other transitions on the same event in document order, and its actions. Raise and assign actions are edited. A typed action is picked from the release's catalogue (`workflows/api.ts`, `GET /api/studio/workflow-actions`), with the permission it needs and its compensation shown, and its parameters as fields generated from its parameter schema (`parameterFields`: a checkbox, a number, a code list or a text).
  - **Right, *Sandbox* mode** (#499; `workflows/SandboxPanel.tsx`, `workflows/sandbox.ts`): central plays the draft, unsaved edits included, with every action stubbed (`POST …/workflows/sandbox`). The browser holds only the run: the guard answers, the gates' outcomes and the moves (an event, or a wait); every change posts it whole and central replays it from the start, so undo and restart are fewer moves and the browser never decides a transition. It shows what holds after the last step (active states, stubbed actions, open tasks, pending timers), *Send* for each event the configuration accepts, *Wait … for* each timer and a free wait, the history, and the guards the next move needs answered when it was not taken. The active states are lit on the canvas and in the outline. *Save as scenario* writes the `workflow-scenario` file central returned, under the author's name, into `tests/` through the same `If-Match` path.
  - **Above:** the publication checks the browser can run (`workflows/model.ts`'s `problems`: the engine's statechart and definition checks, and, once the catalogue is read, each action reference and parameter and the workflow principal's permissions), rerun on every edit, each selecting its element. A timer or eventless step runs as the workflow principal, so it must hold the permission of each action the step runs (its own and its targets' entry actions): the problem offers *Declare* for it, and a declared permission no action needs offers *Remove*. Declared permissions are approved at publication. *Check now* remains the authority, and runs the scenarios.
  - Selection is shared: the outline, the canvas and the problems all select the same element. Everything the canvas does can be done from the outline and the inspector with the keyboard.
  - **Saving** goes through the file editor's path: the Library, its definition re-encoded as its inline content, with `If-Match`. What the Studio does not edit (exit actions, the data model) is kept as read.
  - **Decision tables** (#516; studio.md § Decision tables) are listed above the canvas, each opening `workflows/DecisionTableEditor.tsx` in place of the three columns; *New decision table* creates one, and a malformed table's problem opens it. The editor has the checks above (gaps when there is no default, rules that never fire, failing test cases, rerun as the author edits by `POST …/decision-tables/check`), the data requirements whose paths are its inputs, the rules in order (name, outcome, *fires* and *never fires*, reorder, *Add rule*), the open rule's all / any / not tree with the FHIRPath it saves as, and *Try a patient* (`POST …/decision-tables/try`: the outcome, the rule that fired and each node ✓ or ✗) with *Save as test*, which writes a `decision-table-test` into `tests/` through the same `If-Match` path. `workflows/decisions.ts` compiles a tree to one expression and parses it back (an expression it did not write is kept as FHIRPath text); it alone maps the engine's `then` (lint forbids the property name). The definition is saved with the Workflow Studio's *Save*.
- **`indicators/conditions.ts`** (#550; studio.md § Indicators, *Criteria*): an indicator's condition tree for the indicator editor (#537), on the decision tables' tree (`workflows/decisions.ts`, whose `compile` and `parse` take the other conditions a tree may hold). *+ date* conditions on any declared date compile against `%periodStart.toDate()`, `%periodEnd.toDate()`, a fixed `@YYYY-MM-DD` or `%previousPeriods.start[N-1]`, and *+ in another indicator* to `'<url>|<version>' in %indicators.numerator` (or `.denominator`); each reads back, and anything else stays FHIRPath text. No screen uses it yet.
- **`indicators/AgeBandSetEditor`** (`/studio/$id/age-bands/$`, #551; analytics.md § Age Band Sets and Population Estimates): an Age Band Set (a `Library` of type `age-band-set`), from the *Age band sets* section (`/studio/age-bands`). A small table: name, unit (days, weeks, months, years), the date age is taken at (the period's end or start, or the date of the care counted), and the from–to rows (both included, an empty *To* open above), with up, down, remove and *Add a band*. `indicators/ageBands.ts` reads and writes the Library's inline content and flags gaps and overlaps on the rows as the author types, naming the ages; *Version* gives the set's own version against the package's previous published one (a band, unit or age-at change the next major, a rename the next patch), which saving writes. Saving goes through the file editor's `If-Match` path. *Check now* remains the authority.
- **`programs/ProgramDesigner`** (`/studio/$id/programs/$`, #500; program-designer.md § The Program Designer): a program package's PlanDefinition, opened from its line in *What changed*, in the files or in the discussion. It assembles; it does not edit (`programs/model.ts`).
  - **The strip:** who it is for (the `program-eligibility` FHIRPath and the EpisodeOfCare type), the care workflow it runs on (the plan's first `composed-of` Library), the scopes the package is active in, and how many override points `configuration/override-points.json` declares.
  - **The journey board:** one column per top-level state of the care workflow, in its order, so stages are added and reordered in the Workflow Studio. Each column has the state's task forms; what happens (task, payment gate, sub-workflow, entry actions, the states inside); its investigations (the ActivityDefinitions of the plan's `action` whose `linkId` is the state, and those its typed actions name); its regimen templates (that action's `at-most-one` group: rules in order, first match wins, each with its FHIRPath condition, its ActivityDefinition and the approved source it cites, with up and down); its timers as the schedule; its outcomes (final states), with the program's Measures on the last stage that has any; and when a patient leaves (events, timers, eventless, guards).
  - **Every linked artefact** shows its kind, its canonical and where it stands: in this draft (added or changed since the previous published version, or a first version), published (unchanged since then, or pinned by the manifest's `depends-on`) or not created yet. *Open* goes to its editor (form designer, Workflow Studio, terminology browser, else the file editor); *Create* writes an empty one at its url and pinned version and opens it.
  - **Reordering** a regimen rule saves the PlanDefinition at once through the file editor's path with `If-Match`; a 412 keeps nothing and offers *Reload*.
  - **The package panel:** the files grouped by kind (the package keeps its artefacts side by side), the missing ones under the group they would go in, and *Still missing*: missing artefacts, regimen templates without a condition, an ActivityDefinition or an approved source, stages the care workflow lacks, and pins to a version the package does not hold. *Check now* remains the authority; publication refuses the same regimen templates (`health-publication`'s `programs`).
- **`PackagesPage`** also starts a blank new package (name, title, kind, first version, canonical base).
- **On the server:** `/api/studio` (`central-server`'s `studio` module, over `health-publication::studio`) lists the actions and their reasons from the lifecycle's own rules, and checks the permission, the stage and the separation of duties again on every step (ADR 0025). The client holds no lifecycle rule: it renders the server's list, in the server's order, and words its refusal codes (`wording.ts`).
- **Not yet:** the indicator, report and dashboard editors (shown as coming soon on the home), *New program* (a program starts as a program package), walking a sample patient through a program (#501), the form designer's conditions other than "is Yes" (not designed yet, studio.md), the Workflow Studio's decision-table guards on transitions (#846), opening a saved scenario in the sandbox (not designed yet), and the other structured editors.
