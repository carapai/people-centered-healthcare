# Analytics: indicators

How program indicators are defined, computed, stored and synced. The decision is [ADR 0068](../adr/0068-indicators-are-fhirpath-measures-computed-on-each-edge.md); the research is [indicators.md](https://github.com/carapai/people-centered-healthcare/blob/research/indicators/docs/research/indicators.md) (branch `research/indicators`).

| Step | Where | What |
|---|---|---|
| Define | Configuration package | A FHIR R5 `Measure`: populations with FHIRPath criteria, stratifiers, scoring. Reviewed and activated like any Published Definition |
| Run | A Report | A Report lays out indicators for one period type; the indicators have no period of their own. Running it reads stored Indicator Reports, on the edge for its facility or at central for any place in scope (`reporting.view`) ([ADR 0070](../adr/0070-reports-are-configuration-that-lay-out-indicators-and-carry-the-dhis2-mapping.md)) |
| Compute | Every Facility Edge Node, and central | The same engine. Each node keeps membership per indicator, period and patient, updated from the change log for changed patients, plus a nightly and period-close run for date-dependent indicators |
| Store | The node that computed it | A summary `MeasureReport` per indicator, period, facility and combination of bands, carrying what its calculation needs to roll up (counts, numerator and denominator, sum and count, minimum and maximum), owned by the analytics module |
| Sync | Edge to central | Summary `MeasureReport`s only. Membership and patient lists never leave the node |
| Roll up | Central | District and national figures are recomputed from summed facility parts, never by averaging percentages. Medians and distinct counts stay at facility level. Central computes cross-facility indicators itself |
| Sign off | Facility, offline | The in-charge (`reporting.submit`) reviews a form's preview for the period and signs it off |
| Send | Central | Posts the signed-off Report to DHIS2 through its cells' mappings ([ADR 0069](../adr/0069-hmis-reports-are-signed-off-at-the-facility-and-sent-by-central.md)) |

- **Periods follow when care happened,** not when it was entered. A late entry marks its period's report changed.
- **Exact counts** go to MoH. Small-cell suppression is for public dashboards only, which are not in v1.
- **Patient lists** (for example, who is overdue) are worklists on the node, not indicators.
- **In code (#548):** `health-analytics` (definition, periods, counting) and `health-analytics-app` (evaluation on the FHIRPath engine). A Measure carries its period date in the `indicator-period-date` extension and what it counts in `indicator-counts`; `basis` names the record type its criteria read, and a count's criteria are its `initial-population`. Each record is evaluated with `%patient`, `%periodStart` and `%periodEnd`. Package test patients are `tests/` files of type `test-patient`; the reference is `packages/reference-packages/anc`.
- **In code (#549):** the calculation is read from the scoring: `cohort` a count, `proportion` a percentage, `ratio` a ratio or, with `indicator-rate-per`, a rate, and `continuous-variable` the `measure-observation`'s `aggregateMethod` (`sum`, `average`, `median`, `minimum`, `maximum`, or `distinct-count`). Its value is its `criteria` or `indicator-value-between` (two dates and a unit), and `indicator-value-pick` takes each person's or enrollment's `first` or `last`. `indicator-cumulative` counts up to the period's end. An enrollment is a record's `episodeOfCare` or `workflow-episodeOfCare`. Criteria read the patient's other resources through `%records`, a `collection` Bundle. Figures are rounded to two decimal places; the summary keeps the exact parts.
- **In code (#550):** date conditions compare a declared date (`<date>.toDate()`) with `%periodStart.toDate()`, `%periodEnd.toDate()` or a fixed `@YYYY-MM-DD`, optionally plus or minus N days, weeks or months; *in the previous N periods* reads `%previousPeriods.start[N-1]`, the start of the Nth period of the Report's type before. *Is in* another indicator is `'<url>|<version>' in %indicators.numerator` (or `.denominator`): evaluation takes the referred indicators from a library (in *Try*, the package's own Measures) and evaluates them over the same period and patients first. Validation refuses an unpinned reference, one to itself, and indicators that refer to each other in a circle. The condition tree that writes and reads both is `apps/client/src/features/studio/indicators/conditions.ts`.
- **In code (#551):** an Age Band Set is a `Library` of type `age-band-set` with inline `application/vnd.health.age-band-set+json` content (`unit`: days, weeks, months or years; `ageAt`: `period-start`, `period-end` or `period-date`; `bands`, each `from` and `to` included, the last optionally open). Validation refuses a gap or an overlap between bands, naming the ages. The semver check compares the decoded content, so a changed band, unit or age-at date is major and a rename a patch. A Measure pins the sets it disaggregates by on its first group's stratifiers (`indicator-age-band-set`, `url|version`), and `Publications::age_band_sets` lists every published version, so a pinned indicator keeps its bands. MoH's sets are in `packages/reference-packages/core` (`ug.moh.core`); the Studio edits one in its *Age band sets* section.
- **In code (#537):** the Studio's indicator editor (`apps/client/src/features/studio/indicators/`) reads and writes a Measure as above (`indicator.ts`), with the condition trees of #550 and *Try* (`POST …/indicators/try`) beside it. *Save as test* writes a `tests/` file of type `indicator-test` (the indicator's `url|version`, the period type and period, and the count, denominator and value as exact decimal text), which submission's simulation evaluates again (`health-publication`'s `indicators::run_tests`), failing the draft when they changed. Disaggregations are not compared there.
- **In code (#552):** a Disaggregation is a stratifier of the Measure's first group: with `indicator-age-band-set` it is by age (the patient's `birthDate`, in the set's unit, at the period's start or end or the record's period date), with `criteria` (FHIRPath) by the code it gives, named by the stratifier's `code`. No birth date, an age in none of the bands or no code is the band `not-recorded`. A counted thing falls in the band of its first record (by period date) in the denominator, or counted when there is none, so the bands add up to the total and a band's numerator is within the band's denominator. The `Summary` carries, per disaggregation, each band's own summary; `Summary::roll_up` rolls them up band by band. Evaluation takes the pinned sets from the `Library` (`with_age_band_sets`), and a set it does not hold is an error. *ANC 1st visits* in `ug.moh.anc` is disaggregated by MoH's ANC age bands.
- **In code (#554):** a Facility Edge Node computes its facility's indicators from its change log, offline (`health-node-api`'s `indicators`, a task beside the workflow upkeep, every 5 seconds). The indicators are the active packages' top-level Measures, with the Age Band Sets they pin; each is computed for the period types of the active Reports and ADR 0075's standard periods (weekly, monthly, quarterly, financial year from July). Each change concerns the Patient it is or the Patients its version and the one before reference, so a record moved or deleted updates both. A changed patient is evaluated again alone (`health-analytics-app`'s `Indicators::refresh`): their records' period dates place care in periods (`periods_with_care`; a cumulative indicator up to today's period), their membership (`indicator_member`, their records as they came out) is kept for exactly those and forgotten elsewhere, and each period whose membership changed is calculated again from every patient's and kept as a summary `MeasureReport` (`indicator_summary`, keyed indicator, period type, period and facility; `health-analytics-app`'s `report`), or forgotten when no patient has care in it, so the incremental path gives what `Indicators::recompute` gives from scratch. Everything is computed again when the active packages change, every day (for date-dependent indicators), and after a new epoch or a log pruned past where the indicators stand (`indicator_state:node`). A basis record tagged with another facility is left to that facility. Syncing the summaries to central is #555.
- **In code (#555):** each sync round of a node that computes indicators posts `/sync/v1/indicator-summaries` (`health-sync-client`, after the push, while the node is compatible): the summaries whose figures central does not hold (`indicator_summary.sent`; the figures' hash leaves out the computed-at time, so the daily recompute sends nothing new) and the removals of those forgotten since (`indicator_summary_upstream`), 200 at a time, or an empty list so central records the sync. Central (`health-sync-server`) refuses the request when a summary is another facility's or holds any element a summary does not (`health_sync_protocol::summary_problem`: no subject, evaluated resource, contained resource or `Patient/` reference), and otherwise keeps each per facility (`facility_indicator_summary`, keyed indicator, period type, period and facility, with when it was computed and received), a corrected one replacing the old and a forgotten one removed, and the facility's last sync (`facility_indicator_sync`). `health_analytics_app::roll_up` reads them back and rolls an indicator up over a given set of facilities (`health_analytics::roll_up_facilities`) from summed parts, each band likewise, refusing medians and distinct counts. A facility reported when it has a summary for the period or synced on or after its first day (UTC) without one (nothing it counts happened); any other is missing, with its last sync, and adds nothing, so with none reported there is no figure rather than zero. The roll-up carries each reported facility's computed-at and last sync and the newest computed-at. Which facilities make up a district, region or the country is the facility registry's (ADR 0094, #869): `health_facility_registry::Places::facilities_in`, served for the session's place by `GET /api/places/area`.
- **In code (#599):** the data explorer. `Period::range` reads a range of whole standard periods (`STANDARD_PERIODS`: weekly, monthly, quarterly, financial year from July; at most `MOST_PERIODS`), so there are no arbitrary dates; each period is read as stored, since every edge computes every standard type. `health_analytics_app::explore` gives each indicator × period × place its roll-up over the place's facilities (a facility is itself, an area `Places::facilities_in`), or, for a median or distinct count over more than one facility, the reason; one facility's median is its own figure (`roll_up_facilities`). Central serves `GET /api/analytics/explorer` (the session's place and the places below it, the published indicators, the period types) and `POST /api/analytics/explore` over the synced summaries, refusing a place outside the area (403); an edge serves the same over its own summaries (`OwnSummaries`: it has always just synced), offline, for its facility only. Both need `reporting.view`. The client's *Data explorer* (`/explore`) has the pickers on the left and a live column chart, the figures as a table, where and when they were computed, completeness for the latest period, the missing facilities with their last sync, and the facility-only reason.
- **In code (#600):** the explorer also draws a line chart, a table (places × indicators, or indicators × periods) and a single number per indicator and place: the range's last period with its change on the period of the same type before. The chart type is kept apart from the question, so switching it keeps the selection. An indicator's threshold bands (a legend set) are `indicator-threshold` extensions on its Measure, one per band, with `from` (inclusive) and `to` (exclusive) as `valueDecimal`, either absent for no bound, and `tone` (`good`, `warning` or `bad`). Validation refuses overlapping bands, `from` not below `to` and unknown tones (`health_analytics::threshold_bands`); a gap leaves a figure uncoloured. Bars, line points, table cells and single numbers take their band's colour, with a legend under the Visualization. Bands only colour: outbreak alerts stay surveillance's (ADR 0091).
- **In code (#601):** a question may split its figures by one Disaggregation every indicator asked has (`disaggregation`, by name, listed with each indicator by `/api/analytics/explorer`). Each figure then carries its bands in the summary's order (an Age Band Set's, or the codes found, then *not recorded*), each band's figure recomputed from its summed parts, never from averaged percentages. The chart's series are by indicator, by place or by band (the series choice sits beside the chart type, ready for saving), and *Each area under* a place picks the places directly below it.
- **In code (#602):** saved Visualizations and Dashboards are kept at central (`saved_visualization`, `saved_dashboard`; `health_analytics::dashboard`). A Visualization is a title over the explorer's setup (`type`, `question`, `layout`, `series`), and its places may *follow the viewer* (`follow`: `myPlace` or `eachAreaUnder`), so one shared Visualization shows each viewer their own place or the areas under it. `POST /api/analytics/visualizations` saves one, optionally onto one of the session's own Dashboards, with its places in the session's area; `POST /api/analytics/dashboards` and `PUT /api/analytics/dashboards/{id}` (its owner only) set a Dashboard's title and shares: people by username, roles by code, or a place level (*every district*). Saving needs `analytics.author` as well as `reporting.view`. `GET /api/analytics/dashboards` lists the Dashboards the session may open (its own, and those shared with it, matched on its account, its roles at its place, and its place's level), with their Visualizations, and the session's own Visualizations on none of them. The client's *Dashboards* tab (`/dashboards`) lists standard (none yet, #603) and saved Dashboards, draws each item for the viewer's area with *Open in explorer*, and lets the owner share it; the explorer has *Save Visualization*. Saved Dashboards are central's only for now: a facility's users open them online.
- **In code (#604):** a Visualization's `type` may be `map`. District and region boundaries ship in the national core package as `Library/administrative-boundaries` (`application/geo+json`, a `FeatureCollection` of (Multi)Polygons each named by an area's `code`; `health_facility_registry::AdministrativeBoundaries`): Validation refuses them without the package's regions and districts, for an area not listed or twice, as an unclosed ring or a position out of range, or for a district whose boundary lies outside its region's (`health-publication`'s `areas`). `central-server boundaries <package-dir> <boundary-file> [--name <property>]` imports a UBOS/MoH GeoJSON file into a package directory (`import_boundaries`: each feature matched to an area by `code`, else by name). Central's `GET /api/analytics/map` (`reporting.view`) answers the session's area only: the boundary of each district and region in it, from the newest published package holding any, and each open facility with its NHFR coordinates; an edge's answers its facility's point and no boundaries. The client draws a map per indicator for the range's last period as SVG (`features/explorer/map.ts`, equirectangular, no tiles or library, so it works offline): the places asked shaded by their figure's band over the viewer's own place, facilities inside them as points, coloured by their own figure when asked and hollow, with their last sync on hover, when missing for the period. The figures table stays under the map.
- **In code (#603):** standard Dashboards are configuration in a Reporting package, `configuration/dashboards/<id>.json` (schema `dashboard/1`; `health_analytics::standard`): a title and Visualizations in the explorer's setup, whose places always follow the viewer and whose periods are a fixed range or the last *n* of their type (`last`), so one package version stays current. Validation refuses one outside a Reporting package or away from its id's path, an indicator not pinned to `url|version` or not published (or in the package), and a disaggregation an indicator does not offer. `GET /api/analytics/dashboards` lists, to every session with `reporting.view` and before its saved ones, the Dashboards of the newest published version of each package (`Publications::published_dashboards`), their periods resolved as of today (UTC). They cannot be changed in place (`PUT` and saving onto one answer 403); `POST /api/analytics/dashboards` with `copyOf` *saves as* the author's own Dashboard, its Visualizations copied at the author's places, still following the viewer. `ug.moh.hmis` holds *ANC overview*; the local backend publishes a sample Reporting package with one over the sample indicators. On the Facility Edge Node, standard Dashboards wait for the edge's Dashboards tab.

## Reports

Decided in [ADR 0070](../adr/0070-reports-are-configuration-that-lay-out-indicators-and-carry-the-dhis2-mapping.md) and [ADR 0072](../adr/0072-report-sections-carry-their-own-disaggregations-and-line-lists-stay-at-the-facility.md); the designer is in [studio.md § Reports](studio.md#reports).

- A **Report** is configuration in a Reporting package: a title, one period type, the levels it runs for, and sections.
- A **table section** has indicator rows (by `url|version`) and its own Disaggregations, each laid out as rows or columns (several on one side are crossed), with optional column totals, row totals and % change from the previous period.
- A **line list section** has one row per enrollment or per visit, with any attribute or concept as a column. It is patient-level, so facility only.
- **Outputs:** screen, print or PDF, CSV.
- An **HMIS form** is a Report marked *sent to DHIS2*, each cell carrying its DHIS2 mapping.
- **In code (#556):** a Reporting package (`kind` `reporting`, one approver) holds each Report at `configuration/reports/<id>.json`, written to the release's `report/1` schema (`health_packages::REPORT`) and read as `health_analytics::ReportDefinition`: `id`, `title`, `periodType`, `levels`, and `sections`, each `kind` `table` (`disaggregations`, each an `ageBandSet` `url|version` or a `code` with its FHIRPath `expression`, on `axis` `rows` or `columns`; `rows` of `indicator` `url|version` and `label`; `columnTotals`, `rowTotals`, `change`, `sendToDhis2`) or `lineList` (`rowPer` `enrollment` or `visit`, the `program`'s canonical URL, `enrollments` `started` or `active`, `visitTypes`, `countedBy` an indicator, and `columns`, each an `attribute` from `report::ATTRIBUTES` or a `concept` with, on an enrollment row, its `pick`). Validation (`health-publication`'s `reports`) looks indicators and Age Band Sets up in every published package version and the package itself, and refuses medians, distinct counts and line lists above facility level, unpinned or unknown references, totals without a disaggregation on their side, and a Report outside a Reporting package or away from its id's path. The reference package `ug.moh.hmis` holds the HMIS 105 antenatal care Report and the facility's ANC monitoring.
- **In code (#559):** the Report designer (`apps/client/src/features/studio/reports/`) edits a Report as `report.ts` reads and writes it, in the schema's key order. Its preview is `POST /api/studio/packages/{id}/reports/preview`: Validation's problems for the unsaved Report, each with its section (`ReportDefinition::located_problems`), and each table row's figures for the period and, with % change, the one before (`Period::previous`), the whole and each band, evaluated as *Try* evaluates an indicator over the test patients of the Reporting package and of each package version holding one of its indicators. An indicator is taken from the draft, else a published version, else another package's open draft, so a Report can be previewed before its indicators are published. The designer lays cells out from each indicator's own bands (`layout.ts`).
- **In code (#867, part 1):** a cell crossing several of a section's Disaggregations is previewed from the row's `crossed` figures: for its row bands crossed, its column bands crossed, and both, central summarises the counted things in every combination of bands (`Evaluation::crossed`), each with its own numerator and denominator, so the crossed cells across one Disaggregation add up to the band of the others. A line list's concept column is chosen by a terminology search (the package's code systems, searched at central a page at a time).
- **In code (#867, part 2):** the preview shows a line list's rows over the test patients, at facility level (`health-analytics-app`'s `line_list`). The program is its ProgramPlanDefinition (from the draft, else a published version, else an open draft), and an EpisodeOfCare is an enrollment in it when it names the program (`episode-program`) or has its episode type (`program-episode-type`); the test patients of the package holding it are read too. Enrollment rows are those started in the period or active during it (`EpisodeOfCare.period`); visit rows the enrollments' Encounters dated in the period (`actualPeriod.start`), of the visit types chosen. *Only those counted by* keeps a row whose record, or whose enrollment or one of its visits, the indicator counted (`Reason::Meets`). Attributes read the Patient, EpisodeOfCare or Encounter (age in whole years at the visit, or at the period's end); a concept reads the Observations recorded at the enrollment's visits up to the period's end (the visit's own on a visit row): the latest, first, all with their dates, or how many.
- **In code (#879, part 1):** the Dashboard designer (`apps/client/src/features/studio/dashboards/`) edits a standard Dashboard as `dashboard.ts` reads and writes it. Its preview is `POST /api/studio/packages/{id}/dashboards/preview`: publication's problems for the unsaved Dashboard (`health_publication::dashboard_problems`: the file it belongs at, then `StandardDashboard::located_problems`), and each Visualization's figures as the explorer answers them over the last *n* periods as of a given day, computed over test patients and standing for one place (`sample`).
- **In code (#879, part 2):** on a Facility Edge Node, `GET /api/analytics/dashboards` (`health_node_api::analytics::dashboards_here`) lists the standard Dashboards of the active Reporting packages, read from their tarballs (`health_publication::dashboards_in_files`), in central's shape with `canAuthor` false and no saved ones; each item is answered by the edge's `/explore` over its own summaries, its places following the facility (`forViewer`: *each area under* a facility is the facility).
- **In code (#557, part 1):** running a Report reads stored summaries only (`health_analytics_app::reports::run_report`): each table row is the explorer's roll-up of its indicator over the place's facilities for the period and, with % change, the one before, the whole and each band of the section's Disaggregations (matched by name, or an Age Band Set by the set it pins), so a Total is the whole recomputed from summed parts, never an addition of percentages; an estimate denominator divides by the place's estimate as the explorer does, and the run carries the facilities reported out of expected and the missing ones. Central's `GET /api/analytics/reports` lists the Reports of the newest published version of each Reporting package (`Publications::published_reports`) with the places of the session's area at the Report's levels, and `POST /api/analytics/reports/run` runs one for such a place (403 outside the area); an edge lists its active Reporting packages' facility-level Reports and runs them for its facility over its own summaries (`health_node_api::analytics::reports_here`, `run_here`), offline. Both need `reporting.view`. The client's *Reports* page lays tables out with the designer's `layout.ts`, and its screen and CSV export are one grid (`features/reports/api.ts`' `sectionGrid`); printing is the browser's (print or save as PDF). A line list shows no rows at central (it is patient-level).
- **In code (#557, part 2):** a summary keeps, besides each Disaggregation's bands, each crossing of two or more of them (`Summary::crossed`; up to six Disaggregations): every combination of bands something was counted in, with its own parts, as a stratifier naming the Disaggregations in its `indicator-crossed` extensions (in the indicator's order) with one stratum per combination, its bands as `component`s. They roll up cell by cell from summed parts (`Summary::roll_up`), a crossing kept only when every part that counted something carries it, so a summary computed before crossings were kept leaves the crossed cells out (*not every facility's figures carry crossed bands yet*) rather than summing them in part. Central's check of a synced summary (`health_sync_protocol::summary_problem`) takes the crossings' `component` and `valueString` and still refuses any string naming a patient. Running a Report reads a crossed cell from them (`Summary::crossed_at`; a combination nobody had is empty) for the crossings the section lays out, as the designer's preview does. On a Facility Edge Node a line list section runs over the facility's own patients (`health_analytics_app::line_list::facility_rows`): the program is the active packages' PlanDefinition, *only those counted by* reads the indicator's kept membership for the period (so its rows are exactly what the summary counted, and only those patients are read), and enrollments and visits tagged with another facility are that facility's. The *Reports* page shows its rows with the patient first, and the CSV export holds them as on the screen; at central a line list still has no rows (ADR 0072).

- **In code (#560, part 1):** a table section sent to DHIS2 carries `mappings` (`health_analytics::dhis2::CellMapping`): each a `row`, its `bands` by Disaggregation name (a side left out is that side's Total), a `dataSet`, `dataElement` and `categoryOptionCombo`, in effect `from` a day and optionally `to` one, and `zeroIsSignificant`. Validation (`dhis2::section_problems`) refuses a count row's cell (a count or a sum) at a band of every Disaggregation without a mapping, or whose mappings all end (a coded Disaggregation's bands are the codes its mappings name), two mappings of one cell in effect on the same dates, a mapping of a non-count row, of a row or band the section lacks, or with a missing ID or date, mappings on a section not sent, and IDs not in central's recorded copy of the instance's metadata: an unknown data set or one of another period type (`dhis2_period_type`), a data element missing from the metadata or from the data set, a category option combo the data element (or the data set's override) does not take; with no copy recorded, the mappings cannot be checked. The copy is the instance's `dataSets` export (`DataSetsExport`), recorded with `central-server package dhis2-metadata <file> --by <person>` (`Publications::record_dhis2_metadata`, audited; table `dhis2_metadata`, migration `0065`), so Validation never calls DHIS2. The Report designer's mapping sheet edits each cell's mappings (*+ mapping* starts a revision the day after the last one ends), and the indicator editor's HMIS mapping lists each row's cells with their IDs and dates (`GET /api/studio/indicator-mappings`). `ug.moh.hmis` maps HMIS 105's ANC attendance to illustrative IDs, recorded in `packages/reference-packages/dhis2/ehmis-metadata.json`, until MoH's eHMIS metadata is exported. Facility org unit IDs and the *reported through the platform* switch are part 2.

## Age Band Sets and Population Estimates

Decided in [ADR 0071](../adr/0071-population-estimates-ship-as-yearly-population-packages.md).

- **Age Band Sets** live in the national core package (MoH's) or a program package, edited in a small Studio table (name, unit, the date age is taken at, from–to rows, with gaps and overlaps flagged). Changing the bands is a major version; indicators and Reports pin the version.
- **Population Estimates** ship as a yearly **Population** package: estimate types given per place or derived as a percentage of another (expected pregnancies = 5% of total), figures at the lowest level available and summed upward, no guessed shares. A Report's period takes the annual figure pro rata (month 1/12, quarter 1/4, week 7/365).
- **v1 source:** the HMIS lead imports a year's figures at central from a CSV template (UBOS projections), checked against the facility registry and the NHFR, with district totals shown before approval.
- **In code (#553, part 1):** `health-analytics`' `estimates` (`EstimatesDefinition`, `Estimates`, `pro_rata`, `parse_estimates_csv`, `over_estimate`) and the package kind `population`, its estimates at `configuration/population.json` (schema `population/1`; percentages as exact decimal text). A place's own figure wins over the sum of the places below it. A Measure names its denominator's estimate type with `indicator-denominator-estimate` (`valueCode`) on a `proportion` or `ratio` scoring with no `denominator` population; each facility's summary then carries the numerator only, and the place's estimate for the period divides it at roll-up. Central checks the CSV at `POST /api/places/population/preview`; the Studio's *Population estimates* section imports it. The reference package is `ug.population.2026`.
- **In code (#553, part 2):** central's explorer and Dashboards (`POST /api/analytics/explore`) divide an estimate-denominator indicator's summed count by the place's estimate for the period (`PopulationEstimates`, from the newest published version of each Population package, summed up the facility registry; a period takes the year it starts in). Each such figure carries its count and the estimate, and a place with *no estimate* has no figure. An edge keeps only its own facility's figures of its active Population packages (`EstimatesDefinition::for_places`): the signed tarball arrives whole, as every package does, and the node's explorer and Dashboards divide by the facility's own estimate. The Studio's indicator editor picks an estimate type as the denominator (*Denominator from*, #864) from the types the designs listing gives for each Population package. Running Reports over stored summaries (#557) takes the same path.

## Reporting to DHIS2

Decided in [ADR 0069](../adr/0069-hmis-reports-are-signed-off-at-the-facility-and-sent-by-central.md).

- **v1 forms:** 105, 108 and 106a, aggregate only. 033b is computed and signed in the platform and keyed into mTRAC, or sent to DHIS2 where enabled (ADR 0091); case forms print for the district (ADR 0087); electronic case-based surveillance waits for MoH.
- **Mapping:** each cell of a Report sent to DHIS2 maps to a data set, data element and category option combo, with effective dates, checked against the instance's metadata at Validation. Each facility's org unit ID is set at central and checked against the NHFR.
- **Corrections:** changes after sign-off mark the period changed; the in-charge re-signs and central resends the whole form. Lock or approval rejections become a task for the district HMIS focal person. A corrected zero is sent as a deletion unless the cell's zeros are significant.
- **Manual entry:** a per-facility, per-form *reported through the platform* switch at central; overwrite counts from DHIS2's import summary are shown to the in-charge and district.

## Dashboards

Decided in [ADR 0075](../adr/0075-dashboards-read-indicator-reports-only-over-standard-periods.md).

- **A Visualization** is one saved view (chart, table, map or single number) over chosen indicators, periods, places and Disaggregations. **A Dashboard** arranges Visualizations.
- **Summaries only:** at central for district and above, and on the edge for the facility, offline. Medians and distinct counts show at facility level only.
- **Standard periods:** any range of weeks, months, quarters or financial years. There are no arbitrary date ranges.
- **The data explorer** pivots indicators by place, period and Disaggregation, and saves Visualizations.
- **Standard Dashboards** ship in the Reporting package. **Saved Dashboards** are user content (`analytics.author`), shared with a person, role or place level.
- **Scope, freshness and completeness:**
  - Users see their assigned area: the place their role is held at and everything below it (ADR 0094).
  - Each Visualization shows when its data was computed and how many facilities have reported.
  - A facility that has not synced shows as missing, never as zero.
- **Maps:** facility points from the NHFR, and boundaries from the national core package.
- **Thresholds:** values can be coloured by threshold bands. Outbreak threshold alerts are in [surveillance.md](surveillance.md) (ADR 0091).
- **Not in v1:** public dashboards.
- **Layout: explorer first** (decided from the prototype in [How do the data explorer and a Dashboard look?](https://github.com/carapai/people-centered-healthcare/issues/597), branch `prototype/dashboards`, variant A):
  - **Data explorer:**
    - Pickers on the left: data, periods (standard periods only), places in the user's area (or *each area under my place*, which follows the viewer), disaggregation, and series.
    - Chart-type buttons sit above a live Visualization.
    - *Save Visualization* takes a title and optionally a Dashboard.
  - **Dashboards tab:**
    - Dashboards are listed on the left, standard or saved.
    - Sharing is with a person, role or place level, and each viewer still sees only their own area.
    - Each item has *Open in explorer*.
  - **Every Visualization card** shows where it was computed, when, how many facilities reported, the missing facilities with their last sync, and why a median is absent above facility level.
